# えみは受付AI フォローアップ計画

最終更新: 2026-04-09

## 1. 現状メモ

- Apotool の実機ログインはローカルで確認済み。review 承認後に候補枠確認と投入を行う構成は動かせる。
- 未解決の運用論点は `通知チャネル` `電話番号取得精度` `急患/通常の受付境界` の3点。
- v1 は `確認後実行` を維持し、live 通話中に予約確定を約束しない前提はそのまま。

## 2. 論点と方針

| 論点 | 現状 | 方針 | 優先度 |
| --- | --- | --- | --- |
| 通知チャネル | 未実装 | 土曜確認までは保留。必要なら Slack ではなく公式 LINE を第一候補にする | 低 |
| 電話番号取得精度 | 取得はしているが確認ロジックが弱い | 3-4桁区切りの復唱、2回まで再確認、不確実時は unresolved に落とす | 高 |
| 急患/通常の区分け | triage 型はあるが通常のみ固定にし切れていない | v1 は通常受付のみを自動処理し、急患は manual review / 折返しへ寄せる | 最優先 |

## 3. 修正プラン

### 3.1 急患/通常の受付境界を固定する

#### 目的

- v1 の運用を `通常受付のみ` に固定し、急患の誤案内や誤投入を防ぐ。

#### 変更方針

1. `lib/agent-demo-config.ts` の prompt を更新する。
   - 急患っぽい訴えを検知したら live では空き確認に進まない。
   - 返答は `スタッフが優先確認して折り返す` に統一する。
   - `booking_status` は引き続き `pending_manual_confirmation` のままにする。
2. `lib/elevenlabs/memo.ts` の triage 正規化を見直す。
   - 急患ワードや legacy `urgency_level` から `same_day_phone` / `doctor_required` / `manual_review` を安定して出す。
   - `manual_review_reason` に急患判定理由を残す。
3. `lib/appointment-tool/provider.ts` に実行ガードを足す。
   - `triageLevel !== routine` の draft は availability / execute を止める。
   - UI には `急患は自動投入対象外` を明示する。
4. `components/home-page.tsx` の表示を補強する。
   - `routine` 以外は review 承認後でも `人確認のみ` の表示に寄せる。

#### 受け入れ条件

- 急患系の会話で Apotool の候補枠確認や投入に進まない。
- 履歴詳細で `triageLevel` と `manualReviewReason` が確認できる。
- AI の終話文言が `折返し` で終わり、予約確定を言わない。

### 3.2 電話番号取得精度を上げる

#### 目的

- callback 前提の会話で、電話番号の認識ミスを減らす。

#### 変更方針

1. `lib/agent-demo-config.ts` の収集ルールを更新する。
   - 電話番号は `3-4桁区切り` で復唱確認する。
   - 同じ番号確認は `2回まで` に制限する。
   - 不確実なら `phone_number` を確定値扱いしない。
2. `lib/elevenlabs/memo.ts` に電話番号の正規化ルールを追加する。
   - ハイフン有無や全角混在を正規化する。
   - 明らかに桁数が不正な値は `null` に落とす。
3. `components/conversation-provider.tsx` とガードレール層の追加を検討する。
   - 番号確認ループが続いたら `callback前提で unresolved に移す` 指示を runtime で差し込む。
   - これは既存の会話反復ガードと同じ責務に寄せる。
4. review UI を補強する。
   - `phone_number` 未確定時は `要確認` を出す。
   - `unresolved_questions` と `manualReviewReason` に電話番号未確定を残す。

#### 受け入れ条件

- 電話番号が取れたケースでは、保存値が正規化済みの 10-11 桁になる。
- 認識が曖昧なケースでは、誤った番号を確定せず `manual review` に落ちる。
- 既知の誤認識ケースをテストに追加できる。

### 3.3 通知チャネルを決めて実装する

#### 目的

- アポイント実行や折返し要対応を、現場が確実に見るチャネルへ出す。

#### 判断待ち

- 土曜確認までは `通知自体が必要か` を保留。
- 必要な場合は Slack ではなく `公式 LINE` を第一候補にする。

#### 実装方針

1. `NotificationChannel` の adapter 境界を作る。
   - `line_official`
   - `slack`
   - `disabled`
2. 通知トリガーを限定する。
   - review 後の投入成功
   - 投入失敗
   - 急患/折返し判断
3. 通知本文は最小にする。
   - 患者名
   - callback 番号
   - 希望日時
   - triage
   - 対応要否
4. `artifacts` 側の audit と通知を紐づける。

#### 受け入れ条件

- 通知チャネルが `disabled` の時は何も送らない。
- 通知を有効化した時だけ、対象イベントで1回ずつ送信される。
- review UI と audit に通知有無が残る。

## 4. 実装順

1. 急患/通常の境界固定
2. 電話番号取得精度の改善
3. 通知チャネルの決定後に LINE 通知を実装

## 5. 最小タスク分解

### Phase 1

- `routine` 以外を Apotool 実行対象外にする
- prompt を `通常受付のみ` に寄せる
- triage / manual review の回帰テストを追加する

### Phase 2

- 電話番号の復唱確認ルールを prompt に追加する
- memo 正規化で番号をクリーニングする
- 未確定番号を UI で見分けられるようにする

### Phase 3

- 通知チャネルの要否を確定する
- 必要なら LINE adapter を追加する
- 通知イベントと audit を結びつける

## 6. 追加メモ

- Slack 通知は今の現場運用とは相性が弱いので、通知が必要でもデフォルトは LINE 前提で設計する。
- 急患対応を自動化するのは v1 の範囲外。まずは `検知して人へ返す` までに留める。
- 電話番号は `無理に埋める` より `曖昧なら未確定で残す` を優先する。
