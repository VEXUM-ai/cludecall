# アポツール連携リサーチ

最終更新: 2026-04-06

## 1. このメモの目的

このメモは、`デンタル 一次受付AI` から最終的に `アポツール` へ予約を流し込む構想について、`2026-04-06` 時点で公開情報から確認できたことと、現実的な進め方を整理したものです。

前提として、このリポの現行実装は `manual_review` を既定にした安全設計です。まず AI が `AppointmentDraft` と `appointmentToolPayload` を作り、人が確認してから登録するフローを完成条件にしています。この判断は現時点でも妥当です。

## 2. 結論

- 一番安全な進め方は、`本番へ直接書き込まない` ことです。
- 最初の実運用は `試験用アカウント + ダミー患者 + manual_review` で始めるべきです。
- 公開情報ベースでは、`Apotool & Box` に外部から直接書き込むための公開 API / Webhook / developer docs は確認できませんでした。
- ただし、アポツール側には既に `Web予約機能`、`AI電話予約受付サービス「電話がらくだ」`、`各種機器・レセコン連携` が存在するため、`自動化そのものが不可能` ではありません。
- したがって、現実的な優先順位は `公式Web予約を使う動線` > `ベンダーまたは提携先経由の正式連携` > `承認済みRPA` です。

## 3. 公開情報から確認できたこと

### 3-1. 試験環境の確保は現実的

Apotool の無料体験ページでは、既存契約医院でも無料体験を申し込める一方で、`現在ご利用いただいているアカウントのデータは引き継げませんので、無料体験用の新たなアカウントを作成` と案内されています。  
このため、公開情報上でも `本番とは分離した別アカウント` を作る動線は存在します。

また、お問い合わせページには `デモ環境をみたい・トライアルをしたい` という導線があります。

### 3-2. 公式の自動予約導線は既に存在する

`Web予約機能` では、次が確認できます。

- 予約空き枠のリアルタイム表示
- 診療メニュー選択後の日時提案
- `メニュー別予約リンク`
- ホームページへの空満情報掲載
- Web予約後の問診票やアプリ、LINE への誘導

つまり、`患者が公式Web予約に入れば、その予約は公式導線でアポツールに入る` という経路は既に整っています。

### 3-3. 公式のAI電話サービスはアポツールへ自動反映する

`電話がらくだ` の公開情報では、次が確認できます。

- 予約・変更・キャンセルに自動対応
- 予約枠の代替案提示
- 通話内容のテキスト保存
- 予約情報の SMS 送信
- Web予約への誘導
- 必要時の有人転送または伝言

さらに公開プレスリリースでは、`予約情報及び患者情報を参照し、予約が可能な日時を検索し、確定した予定は「Apotool & Box」へ反映` と明記されています。  
ここから、`Apotool に予約を自動反映する仕組み自体はベンダー内に存在する` と判断できます。

### 3-4. 提携連携の余地はある

公開情報では、Apotool は次のような外部連携を案内しています。

- レセコンとの連携
- 画像機器その他の連携
- `Clinic KIOSK` と `Web予約機能` の連携
- `AI SHIFT` と共同開発した `電話がらくだ`

加えて、ストランザの会社サイトには `サービス、事業連携、取材、採用、ご要望` の問い合わせ導線があります。  
このため、公開 API は見当たらなくても、`事業連携または提携前提の正式連携ルート` がある可能性は高いです。これは公開情報からの推定です。

## 4. 現実的な自動化ルート

### ルートA: AIで一次受付し、公式Web予約へ送る

最も安全で、いまの実装とも噛み合うルートです。

#### 流れ

1. AI が患者情報と希望条件を聞き取る
2. 自院ルールに沿って `service line` を正規化する
3. `service line` ごとの `メニュー別予約リンク` を出し分ける
4. SMS または LINE でそのリンクを送る
5. 患者が Apotool の公式 Web予約画面で最終確定する
6. 予約は公式導線でアポツールへ登録される

#### 長所

- 外部からアポツールへ直接書き込まない
- 空き枠検索、主担当制、特定メニュー制限などを公式機能側に委ねられる
- 予約確定の責任境界が明確
- ベンダー非公開 API に依存しない

#### 短所

- AI がその場で確定完了まではしない
- SMS または LINE の到達率と患者の再入力負荷に依存する

#### このルートが向くケース

- まず事故を避けたい
- 本番への直接書き込みをまだ許可したくない
- 先方 API の有無が未確認

### ルートB: ベンダーまたは提携先経由で正式連携する

`最終的に自システムから直接予約を作成したい` 場合の本命です。

#### 流れ

1. ストランザへ `事業連携` または `自動予約の外部連携` を問い合わせる
2. `API / Webhook / partner interface / sandbox` の有無を確認する
3. もし正式な連携仕様があるなら、`AppointmentToolAdapter` の実装先をそれに差し替える
4. `manual_review -> auto_after_review -> direct_auto` の順で段階導入する

#### 長所

- 将来的に一番きれいな形
- ログ、権限、画面変更耐性の面で RPA より強い
- 予約作成だけでなく変更・キャンセル・照会まで拡張しやすい

#### 短所

- 現時点では公開仕様が確認できない
- ベンダー承認や契約が前提になる可能性が高い

#### このルートが向くケース

- 本気で `direct_auto` を目指す
- 継続運用を想定している
- 変更・キャンセルも自動化したい

### ルートC: 公式の `電話がらくだ` に寄せる

もし `自社AI音声` にこだわらず、`アポツールへの自動反映` を最短で実現したいなら、公開情報上はこのルートが最も完成されています。

#### 流れ

1. 音声予約の役割を `電話がらくだ` に寄せる
2. 自社システムは FAQ、事前分類、院内メモ生成、レビューキューに寄せる
3. 予約確定部分は公式の AI電話サービスへ委譲する

#### 長所

- 公開情報上、最も完成している自動反映ルート
- 予約変更、キャンセル、有人転送、SMS までカバーしている
- 先方運用に乗りやすい

#### 短所

- 会話 UX や制御ロジックの自由度が下がる
- このリポで積んでいる独自会話基盤の価値を一部手放す

#### このルートが向くケース

- 自動反映の実現速度を最優先したい
- 独自音声基盤より、安定運用を優先したい

### ルートD: ブラウザ自動操作で投入する

最終手段です。技術的には可能ですが、第一選択にはしません。

#### 流れ

1. 試験用アカウントに限定して Playwright などで画面投入を作る
2. 必須項目、メニュー、担当、時間枠の選択ロジックを固定する
3. 実際の入力ログとスクリーンショットを残す
4. 本番は `auto_after_review` から始める

#### 長所

- API がなくても実現可能
- 実装着手が速い

#### 短所

- 画面変更で壊れやすい
- 契約やサポートの対象外になる可能性がある
- 重複予約や空き枠競合を安全に扱うのが難しい

#### このルートが向くケース

- ベンダーが API を提供しない
- ただし院内で明示承認が取れている
- かつ限定メニューだけに絞れる

## 5. 推奨する進め方

### Phase 0: 今すぐやること

- いまの `manual_review` を維持する
- `appointmentToolPayload` の項目を確定する
- `service_line -> アポツール側メニュー` の対応表を作る

### Phase 1: 試験環境での安全確認

- ストランザへ `試験用アカウント` または `デモ環境` を依頼する
- ダミー患者のみで投入検証する
- 本番と同じメニュー、診療時間、担当制約を再現する

### Phase 2: まずは公式Web予約連携を作る

- `service_line` ごとの `メニュー別予約リンク` を管理する
- AI 会話終了後に患者へ予約リンクを送る
- 送信文面は `仮受付` のままにする
- 人がレビューしたうえで送る運用から始める

### Phase 3: 正式連携の可否を確認する

- `予約作成 / 変更 / キャンセル / 空き枠照会 / 患者照会` の API 有無を聞く
- `sandbox` の有無を聞く
- `RPA` 許容可否を聞く
- `監査ログ` と `権限分離` の運用方法を聞く

### Phase 4: 条件付き自動化へ進む

- `auto_after_review` で試験環境へ自動投入
- 問題がなければ本番の一部メニューだけ展開
- `doctor_required` や `manual_review_reason` があるものは最後まで人確認に残す

## 6. ベンダーへ確認すべき質問

以下をそのまま確認するとよいです。

1. 外部システムから `Apotool & Box` に対して予約作成、変更、キャンセル、空き枠照会を行う API はありますか。
2. 開発検証用の `sandbox`、`デモ環境`、または本番と分離された試験用テナントは提供できますか。
3. 既存契約医院向けに、患者データを含まない `設定複製のみ` の検証環境は作れますか。
4. 外部自動化ツールによるブラウザ操作は利用規約やサポート上で許容されますか。
5. 予約作成時に必須となる項目、予約メニュー識別子、担当者制御、重複制御の仕様を開示できますか。
6. 自社AIからの自動登録を行う場合、推奨される連携方式はありますか。

## 7. このリポで次にやるべきこと

- `service_line -> web予約URL -> アポツールメニュー名` の対応表を docs 化する
- `manual_review` の payload に `webReservationUrl` と `handoffChannel` を追加する
- 会話完了後のアクションを `手動登録` と `公式Web予約送信` に分ける
- ベンダー返答後に `AppointmentToolAdapter` の実装方針を確定する

## 8. 現時点の判断

- `いきなり direct_auto` は避けるべき
- `まず成立させる` なら `AI一次受付 -> 公式Web予約へ誘導` が最善
- `本当に予約を自動反映したい` なら、ベンダー連携可否の確認が必須
- `API がなければ RPA` はあり得るが、最後の手段
